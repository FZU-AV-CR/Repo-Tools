# Upload Functions

This document explains the upload implementation under `upload/`, with a focus on:

- function-level behavior,
- execution flow,
- performance/concurrency controls,
- metadata transformation rules,
- logging and statistics output,
- failure/retry handling.

---

## 1. Modules in Scope

### `async_upload.py`
Primary async implementation for **single-record upload** and shared primitives used by bulk mode.

### `bulk_async.py`
Bulk orchestrator that:
- reads recids from master cache,
- prioritizes by metadata type,
- runs many uploads concurrently with bounded limits and retries.

### `upload_speed_test.py`
Legacy/sync throughput script for comparison and quick transfer benchmarking.

---

## 2. `async_upload.py` — Function Reference

## `fill_cern_metadata(metadata, path) -> dict`
Maps CERN-like source metadata (`<recid>.json`) into Delphi-compatible target structure.

Key behavior:
- Reads source JSON from `path`.
- Updates `metadata["metadata"]` fields (title, publisher, year, description, creators, subjects, file types, experiment, collision info, category, dataset type, event count).
- Parses collision energy from:
  - structured field (`collision_information.energy`), and
  - free text token `ecms=<value>` in abstract description.
- Validates dataset type mapping:
  - recognizes `collision` / `simulated` from source `type.secondary`,
  - warns if existing value is outside allowed domain.

Notes:
- `dataset_type` values expected by downstream logic are domain-limited (Collision/Simulated semantics).
- Energy range parser extracts numeric min/max when possible.

---

## `create_default_client()` / `create_test_client()`
Build NRP async client instances from repository config.

Use:
- `create_default_client()` for remote test/prod-like endpoint.
- `create_test_client()` for local dev endpoint.

---

## `WeightedSemaphore`
Custom weighted concurrency limiter.

Purpose:
- normal semaphore only counts “tasks”.
- weighted semaphore counts “resource cost”.

Used for uploads:
- lightweight upload => weight 1
- multipart upload => weight 5

This allows enforcing “total upload capacity” while penalizing expensive transfers.

---

## `_upload_with_limiter(...)`
Wrapper around `client.files.upload(...)` that routes upload through `WeightedSemaphore` if provided.

Behavior:
- Computes weight from `transfer_type` (`M` => 5, otherwise 1).
- Executes upload under limiter slot.

---

## `_upload_one_file(...)`
Uploads one dataset file using:
- per-record local semaphore (`file_concurrency`) and
- global weighted upload limiter.

Also auto-selects transfer type:
- `M` for files > 10 MiB,
- `L` for smaller files.

---

## `_write_stats(stats_path, fmt, payload)`
Writes per-record stats in:
- `jsonl`, or
- `csv`.

Fields are generated by `upload_record_async` finalizer and include status, timing, count, and bytes.

---

## `ensure_zip(dataset_files, zip_path)`
Ensures a dataset archive exists and is usable.

Current behavior:
- Works with “original files may be deleted after archiving”.
- If archive exists:
  - appends missing files,
  - checks timestamps for outdated entries,
  - removes original files once considered handled.
- If archive missing:
  - creates new zip and removes originals after adding.
- If no originals and no zip:
  - logs warning.

This supports resumable/recoverable flows for large datasets.

---

## `ensure_zip_async(...)`
Async wrapper for `ensure_zip(...)`:
- executes zip work in thread (`asyncio.to_thread`),
- optionally gates with zip semaphore (limits concurrent zipping tasks globally).

---

## `upload_record_async(...)`
Core per-record async pipeline. This is the most important function in the upload system.

Inputs:
- `recid`, `data_dir`, `metadata_dir`
- template path
- concurrency controls (`file_concurrency`, `upload_limiter`, `zip_sem`)
- stats output settings

Flow:
1. Resolve metadata file and dataset folder.
2. List dataset files and compute size.
3. Load Delphi template and fill it via `fill_cern_metadata`.
4. Create draft record via async client.
5. Update record identifiers/file types.
6. Upload original metadata JSON file (`<recid>.json`) always.
7. Upload data:
   - if file count > 20 => ensure/upload zip as multipart (`M`),
   - else upload files individually in bounded parallelism.
8. Publish record.
9. Emit structured stats in `finally` (success/failure).

Stats include:
- `recid`, `status`, `error`,
- start timestamp and duration,
- file count,
- zip-used flag,
- uploaded bytes estimate.

---

## `setup_logging(level=logging.INFO)`
Configures application logging and suppresses noisy third-party loggers:
- `nrp_cmd`, `urllib3`, `aiohttp`, `botocore`, `boto3`, `asyncio`.

Purpose:
- keep console readable during huge batch runs.

## 3. `bulk_async.py` — Function Reference

## `_load_master_recids(master_cache) -> list[int]`
Loads recids from a master cache JSON.
- Supports dictionary payloads.
- Accepts recid from key or embedded `value["recid"]`.
- Returns unique sorted integer recids.

---

## `_is_collision(metadata_path) -> str`
Classifies metadata into one of:
- `"collision"`
- `"simulated"`
- `"none"` (present but not classified)
- `"missing"` (metadata file not found)

Used for upload ordering priority.

---

## `_upload_with_retries(...)`
Retry wrapper around `upload_record_async(...)`.

Behavior:
- configurable retries and linear backoff (`delay * attempt`),
- logs each failed attempt,
- raises after final attempt.

---

## `main_async()`
Bulk upload entrypoint.

Flow:
1. Set paths/config and limits.
2. Load recids from master cache.
3. Classify and reorder:
   - Collision first,
   - Simulated second,
   - none third,
   - missing last.
4. Create shared client and global semaphores:
   - worker semaphore (`max_concurrency`),
   - weighted upload limiter (e.g., 50 slots),
   - zip semaphore (e.g., 2 zip tasks).
5. Spawn tasks for all ordered recids.
6. Gather results and report failures.

---

## 4. Concurrency Model (Current Intended Behavior)

- **Worker concurrency** (`bulk_async.py`): limits simultaneous records being processed.
- **Upload capacity** (`WeightedSemaphore`): limits total transfer pressure.
- **Multipart weighting**: multipart consumes 5 slots.
- **Zip semaphore**: limits simultaneous zip builds/repairs (currently 2).

This model prevents resource spikes across CPU, disk, network, and repository backend.

---

## 5. Upload Policy Rules

1. **Original metadata file upload is mandatory** for each record (`<recid>.json`).
2. If dataset contains **more than 20 files**, use zip-based upload.
3. Zipping logic supports repair/update and deleted originals.
4. Small datasets are uploaded as individual files with bounded concurrency.

---

## 6. Structured Performance Logging

Per-record stats are persisted by `upload_record_async`:
- `status`: `ok` / `failed`
- `error`: failure message (if any)
- `duration_s`
- `file_count`
- `zip_used`
- `bytes_uploaded`

Formats:
- `jsonl` (recommended for large jobs),
- `csv` (spreadsheet-friendly).

---

## 7. Operational Guidance for Very Large Jobs

For jobs like 13k recids / tens of TB:
- keep zip concurrency low (1–2),
- keep weighted upload slots bounded (e.g., 50),
- keep multipart weight > 1 (currently 5),
- prefer `jsonl` stats,
- suppress third-party logs (`setup_logging`),
- run a small canary subset before full launch.

---

## 8. Failure and Recovery Notes

Common failures:
- missing metadata file,
- missing dataset folder,
- transient network/repository errors,
- interrupted zip/update state.

Recovery strategy:
- use retry wrapper for transient failures,
- inspect structured stats for persistent failures,
- rerun only failed recids,
- rely on `ensure_zip` fix-up behavior for partially prepared archives.

---

## 9. Minimal Usage Pattern

Single-record (programmatic):
1. Create client.
2. Call `upload_record_async(...)`.
3. Review stats output.

Bulk:
1. Prepare master cache + data/metadata directories.
2. Run `bulk_async.py`.
3. Monitor logs and structured stats file.

---

## 10. Developer Notes

When extending upload logic:
- keep `upload_record_async(...)` as the central per-record contract,
- preserve bounded concurrency (avoid unbounded task creation),
- keep stats schema stable or append-only,
- avoid destructive zip recreation when repair is sufficient,
- maintain classification ordering semantics in bulk mode.
